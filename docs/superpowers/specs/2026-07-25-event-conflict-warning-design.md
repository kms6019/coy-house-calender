# 일정 충돌 경고 (Event Conflict Warning) 설계

작성일: 2026-07-25

## 문제

`events` 컬렉션은 커플 단위 공유다. 두 사람이 각자 일정을 넣지만, 저장 시 기존 일정과
시간이 겹치는지 알려주는 장치가 전혀 없다. 결과적으로 더블부킹이 조용히 발생하고,
당일이 되어서야 발견된다.

## 목표

이벤트 생성/수정 저장 직전에 시간이 겹치는 기존 일정을 찾아 경고 다이얼로그를 띄운다.
사용자는 겹침을 확인한 뒤 취소하거나 그대로 저장할 수 있다.

## 비목표 (YAGNI)

- 빈 시간 찾기 / 자동 재배치 제안
- 캘린더 그리드에 겹침 시각 표시
- 저장 자체를 막는 하드 블록 — 경고만 하고 결정은 사용자에게 맡긴다
- 파트너에게 충돌 푸시 알림

## 설계

### 1. 핵심 로직 — `lib/utils/conflict_utils.dart`

```dart
/// 후보 이벤트와 시간이 겹치는 기존 이벤트 목록. 겹침이 없으면 빈 리스트.
List<EventModel> findConflicts(
  List<EventModel> events,
  EventModel candidate,
)
```

판정 규칙:

1. **종일 이벤트는 검사 대상에서 제외한다.** 후보가 종일이면 즉시 빈 리스트를 반환하고,
   기존 이벤트 중 종일인 것도 후보로 보지 않는다. 휴가·생일 같은 종일 일정은 특정
   시간대를 점유하지 않으므로 충돌로 보면 경고가 과하게 잦아진다.
2. **자기 자신은 제외한다.** `candidate.id`와 같은 `id`는 건너뛴다. 수정 시 자기 자신과
   겹친다고 보고되는 것을 막는다. 반복 이벤트의 전개된 occurrence도 마스터와 같은 id를
   쓰므로 같은 규칙으로 걸러진다.
3. **반복 이벤트는 전개 후 비교한다.** 기존 이벤트를 `expandRecurringForRange`로 후보의
   날짜 범위(시작일 ~ 종료일)만큼 전개한 뒤 비교한다.
4. **구간 겹침 판정은 열린구간이다.** `aStart < bEnd && bStart < aEnd`.
   경계가 맞닿는 경우(앞 일정 종료 == 뒤 일정 시작)는 겹침이 아니다.
5. **`endDateTime`이 null이면 시작 시각과 같게(길이 0) 취급한다.** 위 규칙에 따라
   길이 0인 이벤트는 다른 구간 내부에 있을 때만 겹침으로 잡히고, 경계에 있으면 잡히지 않는다.
6. **제안 상태(`isProposed`) 이벤트도 포함한다.** 제안이 겹치는 것도 알 가치가 있다.
7. 반환 순서는 `startDateTime` 오름차순이다.

후보가 반복 이벤트인 경우, 후보의 첫 회차(폼에 입력된 시작/종료)만 검사한다. 반복 전체
회차를 검사하면 경고가 과해지고, 첫 회차 충돌만 잡아도 대부분의 실수를 걸러낸다.

### 2. UI — `lib/screens/event/event_form_screen.dart`

`_save()`의 Firestore 쓰기 직전에 삽입한다.

```
_save()
  └─ 유효성 검사 (기존)
  └─ candidate EventModel 구성 (기존 로직에서 추출)
  └─ findConflicts(ref.read(eventsStreamProvider).valueOrNull ?? [], candidate)
        ├─ 비어 있음 → 기존 저장 흐름 그대로
        └─ 있음 → 확인 다이얼로그
              ├─ 취소 → return (저장 안 함)
              └─ 그대로 저장 → 기존 저장 흐름
```

다이얼로그:

- 제목: `일정이 겹칩니다`
- 본문: 겹치는 일정을 최대 3건까지 `제목 · HH:mm–HH:mm` 형식으로 나열.
  3건을 넘으면 마지막 줄에 `외 N건`을 덧붙인다.
- 버튼: `취소`(기본) / `그대로 저장`

다이얼로그는 async 경계를 넘으므로 표시 전후로 `mounted`를 확인한다.

### 3. 데이터 흐름

새 Firestore 필드나 컬렉션은 없다. 이미 구독 중인 `eventsStreamProvider`의 캐시된
리스트를 읽어 쓰므로 추가 읽기 비용이 없다.

## 에러 처리

- `eventsStreamProvider`가 아직 로딩 중이면 `valueOrNull`이 null이다. 이때는 빈 리스트로
  간주해 충돌 검사를 건너뛰고 저장을 진행한다. 경고를 못 띄우는 것이 저장을 막는 것보다 낫다.
- `findConflicts`는 순수 함수이고 예외를 던지지 않는다.

## 테스트

`test/utils/conflict_utils_test.dart` — 순수 함수 단위 테스트:

- 겹치는 이벤트가 없으면 빈 리스트
- 부분 겹침을 잡는다
- 완전 포함(한 일정이 다른 일정 안에 있음)을 잡는다
- 경계 접촉(앞 종료 == 뒤 시작)은 겹침이 아니다
- 후보가 종일이면 빈 리스트
- 기존 이벤트가 종일이면 후보에서 제외된다
- 같은 id(자기 자신)는 제외된다
- 반복 이벤트의 다른 날 회차와 겹치면 잡는다
- `endDateTime`이 null인 이벤트가 구간 내부에 있으면 잡힌다
- 결과가 `startDateTime` 오름차순으로 정렬된다

UI 다이얼로그는 위젯 테스트 대상에서 제외한다. 기존 `event_form_screen`은 Firebase
의존이 깊어 위젯 테스트가 없고, 이 기능만 예외를 두면 테스트 하네스 비용이 기능 대비 크다.
수동 확인으로 대체한다.

## 수동 확인

1. 14:00–15:00 일정 생성 → 14:30–15:30 일정 저장 시 경고가 뜬다
2. 경고에서 `취소` → 저장되지 않는다
3. 경고에서 `그대로 저장` → 저장된다
4. 기존 일정을 열어 시간 변경 없이 제목만 수정 → 자기 자신과의 충돌 경고가 뜨지 않는다
5. 종일 일정 저장 → 경고가 뜨지 않는다
